## 三、遗留未修的可选级缺陷（详解）

### 3.1 导出 ps1 在 Windows PowerShell 5.1 下必死（最建议先修）

- **现状**：`Ps1ScriptBuilder.cs:39` 生成的脚本头部有 `$ErrorActionPreference = 'Stop'`，第 57 行有 `& $RocmSdk init 2>&1 | Out-Null`。
- **触发场景**：两个设置单独都对，合起来在 5.1 里是毒药——5.1 会把重定向捕获到的**原生程序 stderr 行包装成 ErrorRecord**，配合 Stop 偏好，`rocm-sdk init` 只要向 stderr 打一行警告/进度（激活类工具很常见），脚本就在这行抛终止性错误退出，ComfyUI 根本不会被拉起。而"右键 → 使用 PowerShell 运行"的默认宿主正是 5.1；PowerShell 7 已修复此行为，但导出说明面向的是系统自带宿主。
- **影响**：导出脚本在"恰好需要它的机器"（rocm-sdk 有告警输出）上 100% 不可用。启动器本体不受影响。
- **修法**（最小）：57 行包 `try { & $RocmSdk init 2>&1 | Out-Null } catch { }`，`$LASTEXITCODE` 判断保留；或该行前临时 `$ErrorActionPreference='Continue'`。补一条"生成脚本含 stderr 输出仍能跑完"的构建测试（Ps1ScriptBuilderTests 直接断言生成的文本包含 try/catch 即可）。约 10 分钟。

### 3.2 git pull 走 clone 时固化的 origin

- **现状**：`RepoService.UpdateAsync` 的 pull 分支执行 `git pull --ff-only`（不带 URL），用的是 clone 时写进 `.git/config` 的 origin——而 clone 的 URL 已被拼上当时的镜像前缀。
- **触发场景**：① 镜像站倒闭或用户换镜像 → pull 永远打旧地址、永远失败（讽刺的是"强制覆盖"路径反而能用当前镜像）；② 用户改了 `RepoUrl` → `QueryRemoteHashAsync` 按新仓库查远端、本地 HEAD 却是旧仓库的，"检查更新"永远显示"有更新"。
- **修法**：pull 改为显式传 URL：`git pull --ff-only {Quote(MirrorPolicy.Github(repo, mirror))} HEAD`——不动 origin，每次用当前配置。约 15 分钟 + 一条测试。

### 3.3 强覆盖更新后旧 .git 覆盖版本号

- **现状**：robocopy 路径 `/XD .git` 不动目标里的旧 `.git`；覆盖成功后写入的 `.last_update_hash` 是新代码 HEAD，但下次启动 `DetectGitHeadAsync` 对 git 检出无条件 `rev-parse HEAD` 回填——读的是**旧 .git** 的 HEAD，把正确 hash 覆盖成过期值。此后"检查更新"重新报"有更新"，且 `.git` 内容与工作区文件已不一致（用户在外部做 git 操作会疑惑）。
- **修法**：`RobocopyUpdateAsync` 目标是 git 检出时，成功后顺带 `PathHelpers.TryDeleteDirectory(<ComfyUIDir>/.git)`（"强制覆盖"语义本就丢弃本地状态；删掉后该目录自然走 robocopy 策略，行为更一致）。约 10 分钟。

### 3.4 AI 入口 UI 冻结

- **现状**：`AiGatewayService.Current`（属性）每次访问都会：`FindNode()` 起一个 `node --version` 子进程并同步 `ReadToEnd`（无超时上限，node 卡顿时单次最多等 5 秒）→ `FindCliEntry()` 递归枚举安装目录找 `cli.mjs`。而 `LogPage.AiAnalyze_Click` 一次点击访问它 2-4 次，全在 UI 线程。
- **触发场景**：每次点"AI 智能分析"按钮界面顿一下；Node 环境异常时表现为"点了没反应 5~20 秒"。
- **修法**：① `AiAnalyze_Click` 开头 `var state = gateway.Current;` 取一次复用（3 行）；② 给 `FindNode` 结果做进程内缓存（node 不会中途装上），`FindCliEntry` 结果在 InstallRoot 不变时也可缓存。约 30 分钟。注意与架构候选 2（AiAnalysisHost）重叠——做了候选 2 此条自然消失。

### 3.6 同秒两次启动覆盖日志文件

`LogService.StartSession` 的文件名精度到秒且 `FileMode.Create`（61 行）：启动秒失败（异常复位 Idle）后 1 秒内重点启动，前一会话日志被截断覆盖。修法：文件名追加毫秒或 4 位短随机段（3 行）。影响小，但排障时丢日志很恼人。

### 3.7 两个并发契约缺口

- **AppStateMachine 无锁**：`ReportLaunch` 来自线程池（Exited 事件、async 延续）、`ReportEnvBusy` 来自 UI 线程。极端交错下订阅者会看到"已停止→环境任务中"的闪变，理论上丢一次变更通知。单用户桌面实害很小，修法是两个 Report 加一把对象锁（5 行）。
- **ProcessService 输出回调无串行化门**：stdout/stderr 两个系统线程**并发**进入同一个 `OutputReceived` 回调；同仓库的 `ProcessRunner` 用 `emitGate` 显式串行化并在注释里写明"宿主 `list.Add` 会静默丢行"。当前订阅方（`Log.Append` 有锁、ready 布尔位）都安全，但下一个直接 `list.Add` 的订阅者会复现 ProcessRunner 踩过的坑。修法：`Start` 里加一把 lock 门（3 行）或在事件注释里声明"可能并发调用"。

### 3.8 OSC-8 超链接 ANSI 未剥

`AnsiStripper` 有意只剥 SGR（`ESC[…m` 颜色序列），但 rich/click/uv 一系工具会发 OSC-8 超链接 `ESC]8;;URL ESC\`——没有 `m` 结尾，整段连 ESC 控制字符原样保留。经 comfy-cli/uv 拉起的 ComfyUI 日志进 AI 分析时：发给模型的材料混入不可见控制符与重复 URL 垃圾；指纹归并对"同一错误、不同链接"拒绝归并。修法：`Strip` 补两条丢弃规则——OSC（`ESC]…` 到 BEL 或 `ESC\`）与其余 CSI（`ESC[…@-~`）；`TryMatchSgr` 的"防吞正文"语义保留给渲染路径。约 20 分钟 + 用例。

### 3.9 MaxToolRounds 与提示词口径漂移

系统提示词承诺"整次分析最多发起一轮联网调用"，代码却是 `MaxToolRounds = 2`（本轮已补了总次数 6 的兜底，但轮数口径仍不一致）。模型不守 prompt 时实际联网可达承诺的数倍。修法二选一：`MaxToolRounds` 降为 1，或改提示词文案。1 行。

### 3.10 工具轮正文粘连

`contentBuilder` 跨轮共享：模型第 1 轮先输出一段前导语（"让我查一下…"）再发 tool_calls 时，第 2 轮的最终回答会与前导语直接粘连成一句。修法：进入工具轮时给 builder 追加 `\n\n`（1 行）。纯观感问题。

### 3.11 机器级 TRITON_CACHE_DIR 语义分歧

用户在 Windows 系统环境变量设了 `TRITON_CACHE_DIR=X` 且启动器自定义层没配时：启动器（`EnsureCacheDirs` 在 env 字典里查不到继承值）写入默认 `<comfy>\triton-cache` 并**覆盖**继承值；导出的 ps1 却保留 X。导出与实际启动行为不一致。修法：`EnsureCacheDirs` 前先读 `Environment.GetEnvironmentVariable` 合并，或在导出说明里记录该差异。

### 3.12 窗口最小尺寸 API 需真机验证

`WindowMinSize`（75 行 P/Invoke 子类化）已删，换成 `OverlappedPresenter.PreferredMinimumWidth/Height`（主窗 640×480、AI 窗 760×560）。API 文档确认存在于 WinAppSDK 1.7+ 且本项目用 1.8，编译通过，但**拖拽行为未实测**——需真机拖到最小确认：限制生效、最大化/还原无异常、不会闪跳。若不生效，回退方案是从 git 历史恢复 WindowMinSize.cs。

- 通用包安装/卸载不检查退出码（`EnvUpdatePage`）：`uv pip install not-exist` 失败后状态行仍显示"结束"；补 `if (code != 0) Append($"[错误] …")`。

## 四、架构候选（未做，详解）

### 候选 1：停止故事收拢进 LaunchService（优先级最高）

- **现状**：「停止一个 ComfyUI」分裂在三处——`LaunchService.StopAsync`（状态流：Stopping→杀树→Idle）、`ProcessService`（进程树强杀 + 残留扫描 + 一次性命令三职责混杂）、`MainWindow.OnAppWindowClosing/ShowCloseWarningAsync`（关窗编排：自己再推导 venv 根、再扫再杀）。本轮修的 5 条严重缺陷（#1 误释放、#2 Starting 停止空转、#3 退出竞态、#14 Win32Exception、#15 关窗三缺陷）全部诞生在这些缝隙里——**bug 已修，但制造 bug 的结构还在**，下一轮改"停止"仍要在三个文件里保持同步。
- **目标形态**：`LaunchService` 成为停止语义的唯一 interface——对外 `StopAsync()` 与 `PrepareCloseAsync()`（返回"需要杀哪些进程/需要取消什么任务"的决策结果），ProcessService 退回纯"托管一个子进程"的深模块，MainWindow 只问"关窗前还有什么要收尾"并展示。
- **收益**：停止/关窗的全部状态转换在一个文件可读；给 `LaunchService` 加 ProcessService 构造注入后，这五类竞态都能写成单测（现在 LaunchService 零测试的根因就是构造函数里 `new ProcessService()` 没有缝）。
- **风险/量**：中。触及启动/停止主路径，需真机回归；约 1 天 + 测试。**建议第一个做**——它同时是候选 6（GUI 样板合并）的前置。

### 候选 2：AiAnalysisHost（AI 就绪流程收拢）

- **现状**：就绪流程散在三层——`LogPage.AiAnalyze_Click` 自己判断 Node 缺失/未安装/已运行三态并决定弹哪个窗；安装/解压/拉起/读 Key 在 `AiGatewayService`；模型列举与异常映射在 `AiAnalysisDialog`。同一个失败（网关没起来）要在三处分别处理，本轮 #12 的四个洞就是各层各修各的产物；3.4 的 UI 冻结（Current 反复 spawn node）也长在这。
- **目标形态**：Core 里一个深模块，interface 只有两个动作：`PrepareAsync(progress, ct)` 返回联合结果 `NeedNode | NeedArchive(下载链接, 目录) | Failed(原因) | Ready(模型列表)`（状态检测一次并缓存），`AskAsync(...)` 发问。所有网络/进程异常在内部映射成结果。界面只负责把结果画成对话框。
- **收益**：不启动 WinUI 就能测"没装 Node""目录不可写""网关拒绝连接"这些路径；A1/#5/#12/3.4 全部收进一处，以后 AI 功能的改动 locality 成立。
- **风险/量**：中低。范围只在 Core + 两个界面文件；约 1-1.5 天。

### 候选 3：EvidenceTools（工具安全策略模块化）

- **现状**：本轮已做单点改进——`AllowTarget` URL 守卫（环回/私网/link-local 拒绝 + 重定向逐跳校验）收在 `WebFetchTool` 内，WebSearch 换共享 HttpClient，客户端加了总次数兜底。但"模型能对外做什么"的规则仍分散：轮数在 `AiDiagnosticsClient` 循环里、总次数在另一处、工具名白名单在 `CompositeToolExecutor` 与客户端各查一遍、URL 守卫在 WebFetchTool 私有方法里。
- **目标形态**：独立 `EvidenceTools` 模块内部持有：共享 HttpClient、URL 守卫、调用预算（总次数/单轮次数）。客户端循环只问一句"这些调用允许吗、结果是什么"。
- **收益**：安全规则只有一个入口，改规则不碰提示词；规则可用假 HttpMessageHandler 逐条测试（现在 WebFetch 只有"拒绝非 http"一条测试）。
- **风险/量**：低。纯 AiDiagnostics 库内重构，不动 GUI；约半天。

### 候选 4：B2 通用 Runtime 迁库

- **现状**：`ProcessRunner` / `CommandLine` / `AnsiStripper` 住在 AiDiagnostics 库里，但 AI 网关化后该库自己不再启动任何进程——实际使用者全是 Core（git/uv/pip/robocopy/日志渲染）。README 的依赖方向 `GUI → Core → AiDiagnostics` 因此背了一段与 AI 无关的依赖。且全仓有四套进程启动方式：ProcessRunner（一次性）、ProcessService.Start（ComfyUI 常驻）、`AiGatewayService.Start` 自己 `Process.Start`（**无 Exited 订阅**，node 崩溃只能靠下次探测懒发现）、FindNode 的裸 `Process.Start`。
- **目标形态**：通用 Runtime 迁回 Core（或独立小库），进程入口收成两个：`RunToCompletion`（超时/取消/输出回调）与 `SpawnManaged`（常驻、可停止、树杀、Exited 事件）；网关与 ComfyUI 都走第二个。
- **收益**："stdin 必须关闭""不等管道"这几条硬规则只在一处；网关进程获得 Exited 事件（孤儿/崩溃即时可见）。
- **风险/量**：**高**——搬家 + 合并，不改行为但触及全部进程路径，回归面大。建议单独分支、与候选 1 分开做。约 2 天。

### 候选 5：B3 ComfyVersion 模块（适合热身）

- **现状**：标题栏/主页显示的"当前版本"由四个类拼出（`AppServices.CurrentVersionHash` / `RefreshVersionFromGitAsync` / `RepoService.DetectGitHeadAsync` / `ReadComfyVersion`），HomePage 与 MainWindow 各写一份"后台刷新并回填文本"。还有一个已核实的行为问题：`DetectGitHeadAsync` 每次读 HEAD 都**改写** `.last_update_hash`（RepoService.cs:76），该文件语义从"上次更新到的版本"漂移为"当前 HEAD"，与 3.3（旧 .git 覆盖）相互放大。
- **目标形态**：一个 `ComfyVersion` 模块：`Current`（同步缓存值）、`RefreshAsync()`（只读，不写文件）、`Changed` 事件；两个界面订阅事件。
- **收益/量**：优先级与失败降级只有一份，可测"git 缺失""外部 pull 后"；体量最小（约半天），适合当下一轮的热身或试验流程用。

### 候选 6：GUI 样板合并（约 −130~160 行）

- **现状**：六页 code-behind 里五套样板各自复制——全局任务外壳（EnvUpdatePage.RunOpAsync vs HomePage.RunDirLinkOpAsync，~25 行）、窄/宽两态行重排（ArgsPage 68 行 vs EnvVarsPage 47 行）、窄窗口阈值 SizeChanged（5 处，阈值 640~760 各不相同）、"读配置→回填→写回+Save"绑定、Idle 守卫。

### 候选 7：EnvCapabilities.Evaluate（按钮规则下沉）

- **现状**：`EnvUpdatePage.ApplyGuards` 用状态/工具/目录/venv/架构共同决定 13 个按钮的 IsEnabled——这是纯规则，却只能在 WinUI 里运行、零测试；HomePage 的 `RefreshState`、`RowOpsAllowed` 又各算一遍类似条件。
- **目标形态**：Core 里一个纯函数 `EnvCapabilities.Evaluate(状态, 工具, 配置) → 记录`，每个按钮一个布尔 + 一条"为什么不可用"的原因文本；页面只把记录绑到按钮（不可用原因还能直接当 ToolTip，是体验增益）。
- **收益/量**：规则可表格化测试（"git 缺失时克隆不可用且提示原因"）；约半天。收益取决于后续是否继续往这几页加功能。
