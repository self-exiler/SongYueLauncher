**批次 3 执行中的一处实测修正**：原报告与两份走查都只提「无超时的 `WaitForExit()`」。实际动手后发现 **`WaitForExitAsync()` 同样会被孙进程继承的管道拖住**（`start /b` 派生孙进程的场景两者都等满 15.4 秒），所以单纯把 `WaitForExit` 换成 `WaitForExitAsync` 并不能修好 F-05。正确做法是用 `Process.Exited` 事件判定进程退出，残余输出交给 3 秒冲刷兜底。已补回归用例 `RunCommandAsync_ReturnsPromptlyWhenGrandchildHoldsThePipe`。

## 3. 批次 1：torch 链路恢复（F-01 + F-02）

### F-01 `uv pip download` 不存在 —— 功能当前完全不可用

**证据（实机）**：

```
$ uv --version
uv 0.11.19
$ uv pip download torch -d /tmp/dltest --python .../python.exe
error: unrecognized subcommand 'download'
EXIT=2
```

`uv pip` 的子命令只有 compile / sync / install / uninstall / freeze / list / show / tree / check，从来没有 `download`。【C】判断正确，且**不是版本差异问题**。

**影响**：`WheelService.cs:169-178` 用 `args.Replace("pip install", "pip download")` 拼出命令行，必然 `dlCode != 0` → 每次 torch 更新在 `[2/6]` 中止并报「下载失败」。因为流程是「先验证后卸载」，环境没被破坏，所以一直没暴露。

**改法**（Q-03 拍板后执行）：把 `--download` 验证门换成 `uv pip install <specs> --dry-run`（已确认 `uv pip install` 支持 `--dry-run`），只做解析与索引可达性校验，秒级、不落盘。

### F-02 回滚索引不按 arch 选

**证据**：

- `WheelService.BuildTorchInstallArgs`（:43-51）：`gfx942 / gfx950` 走 `LegacyStagingIndexUrl`，其它 arch 走 `RocmNightlyIndexUrl`。
- `RollbackAsync`（:230）**无条件**用 `RocmNightlyIndexUrl`。

**后果**：gfx942 / gfx950 上安装失败触发回滚时，拿快照版本去 nightly 索引找（该 arch 不在那里）→ 必然回滚失败，还输出「原版本可能已从 AMD 源下架」这句误导性提示。

**改法**：`RollbackAsync` 增加 `arch` 参数，索引选择复用 `BuildTorchInstallArgs` 的同一判定；提示文案区分「索引不匹配」与「版本下架」。

**验收**：`WheelService` 两条路径的参数构造各补 1 条纯函数测试（`gfx942 / gfx1100` 各一），断言索引 URL 与回滚 URL 一致。

## 4. 批次 2：版本号与更新检查（F-03 + F-04）

### F-03 检查更新失败被当成「有更新」

**证据**：`RepoService.cs:41` 丢弃 `runner.Run` 的返回值，失败时 `lines` 为空 → 返回 `""`；`EnvUpdatePage.xaml.cs:225-226` 判断 `remote.Length > 0 && remote == local`，不成立就落到「（有更新）」。

**可复现场景**：镜像不可达、仓库私有、网络断流（`git ls-remote` 退出码 128）——都会显示「有更新」。

**改法**：`QueryRemoteHashAsync` 返回 `string?`，失败返回 `null`；UI 改三态：

| 返回值 | 展示 |
| --- | --- |
| `null` | 远端版本未知（附「检查失败」说明） |
| `""` 或与 local 不等 | 有更新 |
| 与 local 相等 | 已是最新 |

### F-04 版本号来源不对

**证据**：`RepoService.cs:68 / 89 / 128` 三处在 pull / clone / robocopy 成功后再调 `WriteHashFromRemoteAsync`（→ `git ls-remote`，走镜像）。两步之间远端若有新提交，写进 `.last_update_hash` 的就不是本地实际代码。

**改法**（三条路径）：

| 路径 | 取值方式 |
| --- | --- |
| git 检出 + pull | pull 成功后 `git rev-parse HEAD` |
| 非检出 + clone | clone 后 `git rev-parse HEAD`（即远端 HEAD） |
| 非检出 + robocopy | **在 `TryDeleteDirectory(tempDir)`（:121）之前**从临时 clone 取 `rev-parse HEAD` |

**附带收益**：省掉一次经镜像的网络往返，`WriteHashFromRemoteAsync` 这个只在成功后调用的私有方法可整体删除。

## 5. 批次 3：进程与日志基础设施（F-05 + S-06 + F-06 + F-07）

这一批的四项是**同一片代码的四个面**，一起改可以只做一次进程语义回归。

### F-05 + S-06 合并处理：`RunCommandAsync` 改走 `ProcessRunner`

**证据**：

- `ProcessService.cs:181` 有 `try { process.WaitForExit(); }`（注释：冲刷异步输出），**无超时**。
- 这是 `ProcessRunner` 注释里第 3 条硬规则明令禁止的模式（「被拉起的孙进程可能继承 stdout/stderr 句柄，导致进程结束后管道仍不关闭」）。
- `RunCommandAsync` 是 `TaskRunner.Run` 的**唯一出口**——所有环境任务（uv / git / robocopy / 轮子安装）都走它。
- 危险窗口：子进程已退出但孙进程仍持管道 → `WaitForExit()` 永不返回 → 任务槽不释放、界面永久卡在「进行中」，此时取消按钮也只 Kill 直接子进程（已退出），无从恢复。
- 同时 `ProcessService.cs:208-223` 的 `CreateStartInfo` 与 `ProcessRunner.cs:132-145` 几乎逐字相同（【C】与【D】都指出了）。

**【D】在这里有个内部矛盾**：D2 主张删掉 `RunCapturedAsync` 转发，D6 又主张让 `RunCommandAsync` 调用它。正解是**两者都指向 `ProcessRunner.RunCapturedAsync`**（AiDiagnostics 里的真实现），Core 的转发壳照删。

**改法**：`RunCommandAsync` 内部改为调用 `ProcessRunner.RunCapturedAsync`，把分离的 stdout / stderr 按到达顺序合并回调给 `onOutput`；删除 `ProcessService.CreateStartInfo`。合并顺序用现有的单回调机制（`RunCapturedAsync` 已有 `onOutputLine`），必要时给它加一个「行来源」标识以保持前缀区分。

**验收**：
1. 现有 `ToolchainService` / `WheelService` / `RepoService` 全链路跑一遍（工具链检查 + 一次 `git ls-remote`）。
2. 人为构造孙进程持管道场景（`cmd /c "start /b ping -t 127.0.0.1 & exit"`），确认任务能正常结束。

### F-06 优雅停止从未生效

**证据**：`ProcessService.cs:225-234`。`SendCtrlBreak` 做的是 `AttachConsole(pid)` + `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pid)`。

比【C】原判断更严重的一层：`GenerateConsoleCtrlEvent` 的第二个参数必须是**由 `CREATE_NEW_PROCESS_GROUP` 创建的进程组 id**。GUI 无控制台、`Process.Start` 也不提供该 flag，所以 pid 不是进程组 id → 调用返回 FALSE 且不抛异常 → **CTRL_BREAK 从未送达**，每次停止都是等满 5 秒再整树强杀。

**改法**：保持 `SetConsoleCtrlHandler(NULL, TRUE)` 先忽略自身，然后 `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, 0)`（组 0 = 该控制台全体），再 `FreeConsole()`。

**验收**：实测一次「停止」，耗时从 5 s 降到 1 s 内。

### F-07 `LogService.Append` 每行读 `Count`

**证据**：`LogService.cs:53` `while (_buffer.Count > Capacity && _buffer.TryDequeue(out _)) { }`。`ConcurrentQueue.Count` 是 O(1) 但需遍历并锁住所有段，ComfyUI 高频输出下确实是白花。

**改法**：改 `lock` + 普通 `Queue<string>`。

**一处措辞修正**（【C】原文）：「`Clear()` 没加锁」**现在不是 bug**（`ConcurrentQueue` 本身线程安全），改 `Queue` 之后才必须补锁——这是改法带来的新义务，不是现状缺陷。

### S-18 `ArgsBuilder.BuildOne` 分支归并（仅【D】提出）

【D】的事实核验：`BuildOne`（:27-87）确实是 7 个 case 组。归并方向成立：

| 现有组 | 归并后 |
| --- | --- |
| `Flag` | 保留（直接输出 flag） |

## 10. M-01：ComfyUI-Manager 通道镜像接管（功能，非整改）

完整评估见 `docs/评估-ComfyUI-Manager通道镜像接管.md`。这里只并入结论，**不混入代码整改批次**。

- **为什么现有 `GITHUB_ENDPOINT` 接不到**：Manager 唯一消费点是 `glob/git_utils.py:83-84`，判定条件 `url.startswith('https://github.com/')`，`raw.githubusercontent.com` 永不匹配。
